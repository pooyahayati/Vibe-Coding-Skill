# Specialist Authority Contract

Apply this contract when Vibe delegates work. Direct standalone use keeps the specialist's own workflow subject to the host's actual instructions.

Actual system/developer/user instructions and applicable project rules remain authoritative. Within skill composition, Vibe engineering controls override specialist standalone defaults. These are instruction boundaries, not an operating-system sandbox or additional permission grant.

## Allowed within the assignment

- Inspect the assigned context and relevant authoritative sources.
- Recommend domain decisions and implement only assigned surfaces within existing authorization.
- Run checks tied to changed behavior, acceptance criteria, and meaningful failure modes.
- Return decisions, required/optional findings, actual evidence, uncertainty, and unresolved risks.

## Head-owned decisions

Vibe retains the objective, scope, stack, architecture, risk floor, approvals, dependencies, test selection, cross-domain integration, merge/release/deployment authorization, and final acceptance. Do not restart an entire standalone lifecycle for a stage-specific assignment.

Preserve settled decisions. Do not independently expand scope, install arbitrary linked skills/tools, start other agents, evaluate coding models, publish, or deploy. A dependency link is a request for the Head, not unrestricted installation authority. Honor existing user authorization; raise only a genuinely new material user-owned decision.

## Verification and conflicts

Reuse sufficient existing evidence and choose the cheapest useful checks. Specialist defaults must not mandate unrelated full suites, coverage quotas, duplicate checks, or repeated approval questions. Required relevant checks and explicit project policies still apply. Missing evidence stays unverified; scope reduction must not hide a real failure or vulnerability.

When evidence contradicts the assignment, return the conflict to the Head. Head precedence does not permit dismissing valid security findings or weakening the known risk floor.

## Platform constraints

Use the actual project stack and platform APIs. Generic JavaScript/TypeScript examples do not require Node tooling in PHP/WordPress work. WordPress capabilities, nonces, public APIs, lifecycle/data preservation and WooCommerce compatibility remain integration invariants. API conventions must preserve existing consumer contracts and legitimate compatibility windows. Treat security snippets as examples: use explicit public response fields and platform-appropriate CSRF/authorization controls.

## Stage-specific handoff

Input: current stage, objective, affected surfaces/files, settled decisions, platform/runtime, protected invariants, risk floor, authorized actions, acceptance criteria, and evidence expectations.

Output: domain decisions, changed surfaces, preserved constraints, evidence and its revision/environment, checks not performed, required versus optional findings, unresolved risks, and next action for Vibe. Debugging returns a reproduction, root cause or remaining hypothesis, bounded fix, and meaningful regression evidence. Specialist completion never establishes whole-project completion.

The roadmap's [shared improvement contracts](shared-improvement-contracts.md) specifies future assignment/return identities and separate Head acceptance. Current installation/package validation does not implement that semantic acceptance; P0 does not change specialist authority or freshness policy.
